## Introduction

This post analyses a [spam bot malware sample](https://www.virustotal.com/gui/file/36684cef31a4a43473d5b12d30aabf94f56e407b0eeec14b7c1cb87efa3159b6/details) using Ghidra and Python. The primary goal is to reverse engineer all cryptographic subsystems (e.g. config encryption, C2 obfuscation, email composition and signing) and document the vulnerabilities that can be exploited (e.g. for detection and decryption). Additionally, we build a Python config decryptor and provide YARA and capa rules for detection.

## Executive summary

This sample is an x86 PE executable that installs as a Windows service with `SERVICE_AUTO_START` persistence. Encrypted configuration is stored in PE resource `RT_RCDATA/0xE2` using Blowfish-ECB with a hardcoded 16-byte key. The config contains the C2 host, two ports and a service display name in the format `host:port1/port2;ServiceName`.

C2 communication uses UDP with a XOR cipher keyed by the MD5 hash of the ASCII string `"UNREGISTERED"`. No authentication is performed. HTTP downloads (SMTP credentials, email templates, email lists, etc.) bypass TLS certificate validation (via WinINet flags `0x80803100`). Downloaded payloads pass through base64 decode --> XOR decryption --> ZIP extraction with no authentication.

The SMTP engine uses a multi-threaded architecture with a protocol state machine. Authentication supports STARTTLS, AUTH LOGIN, CRAM-MD5 and AUTH PLAIN, but is vulnerable to STARTTLS stripping. Email attachments use the obsolete PKWARE Encryption (ZipCrypto). Email signing supports both DomainKeys and DKIM, but defaults to `rsa-sha1`.

The following subroutines related to cryptographic capabilities have been reversed and their vulnerabilities documented. They are grouped into three categories: custom cryptographic subroutines, PRNG weaknesses and protocol/configuration issues.

Cryptographic subroutines:

| # | Severity | Name | Address | Impact |
|---|----------|------|---------|--------|
| 1 | Critical | Static XOR key (MD5 of "UNREGISTERED") | `0x004680d0` | Decrypt all C2 traffic globally. |
| 2 | High | Blowfish-ECB hardcoded key | `0x00472da0` | Extract config from any sample. |
| 3 | High | Traditional PKWARE Encryption (ZipCrypto) | `0x0047f7b0` | Decrypt all attachments. |
| 4 | Medium | HMAC-MD5 for CRAM-MD5 | `0x0044bf00` | Offline dictionary attack on credentials. |
| 5 | Low | DomainKeys hardcoded rsa-sha1 | `0x00433f40` | Signature rejection. |
| 6 | Low | DKIM defaults to rsa-sha1 | `0x00431880` | Signature rejection. |

PRNG weaknesses:

| # | Severity | Name | Address | Impact |
|---|----------|------|---------|--------|
| 1 | High | Predictable PRNG seed | `0x0047f7b0` | Replay `rand()` to recover ZipCrypto headers. |
| 2 | Medium | `weak_random` 15-bit output space | `0x0044e700` | Predictable random tokens across SMTP engine. |

Protocol and configuration flaws:

| # | Severity | Name | Address | Impact |
|---|----------|------|---------|--------|
| 1 | Critical | No C2 authentication | `0x00426e80` | Spoof commands, hijack botnet. |
| 2 | Critical | TLS cert validation disabled | `0x00466b60` | MITM on all HTTPS. |
| 3 | Critical | No download authentication check | `0x00466b60` | Replace campaign data via MITM. |
| 4 | High | STARTTLS stripping | `0x004437d0` | Capture SMTP credentials. |

## Prerequisites

After the initial analysis we can move to a more in-depth analysis using Ghidra. But before we do that, we need to do some preparations.

### GhidraFindcrypt

[GhidraFindcrypt](https://github.com/antoniovazquezblanco/GhidraFindcrypt) is a Ghidra plugin that identifies cryptographic algorithms by scanning the binary for known magic constants, IVs, etc.. Automatically adds labels during auto-analysis (e.g. `CRYPT_Blowfish_p_init` and `CRYPT_CRC32_m_tab`).

### BSim

[BSim](https://github.com/NationalSecurityAgency/ghidra/blob/master/GhidraDocs/GhidraClass/BSim/BSimTutorial_Intro.md) is a Ghidra plugin that matches unknown functions against known libraries using cosine similarity on decompiler-derived feature vectors.

Since we know the compiler and OpenSSL versions (`Microsoft Visual C/C++(18.00.40629)[C]` and `OpenSSL 1.0.2g  1 Mar 2016`) we can prepare some binaries that will greatly help/speed up the reversing process. This means that we need to build OpenSSL from source using that compiler version. We can use the build artifacts (crypto and SSL libs) with BSim to resolve functions based on similarity. We can do the same with libc functions, for that we need the libc library that is shipped with the compiler (`libcmt.lib`). We will also need the `.pdb` for each file as well (debug info/symbol names).

Prerequisites:
- [Microsoft Visual C/C++(18.00.40629)[C]](http://download.microsoft.com/download/A/A/D/AAD1AA11-FF9A-4B3C-8601-054E89260B78/vs2013.5_ce_enu.iso)
- [OpenSSL 1.0.2g sources](https://github.com/openssl/openssl/releases/download/OpenSSL_1_0_2g/openssl-1.0.2g.tar.gz)
- [perl](https://strawberryperl.com/)
- [nasm](https://nasm.us/)

Build instructions (refer to `INSTALL.W32` in the OpenSSL sources root):
- install the prerequisites
- unzip the OpenSSL sources
- open a `cmd` prompt
- `cd "C:\Program Files (x86)\Microsoft Visual Studio 12.0\VC"`
- `vcvarsall x86` (setup the build env)
- `cd` into the root of the OpenSSL sources
- `perl Configure VC-WIN32 --prefix=C:\openssl`
- `ms\do_nasm`
- `nmake -f ms\ntdll.mak`

We need the following built libraries:
- `libeay32.dll` (crypto) + `libeay32.pdb` for symbol names
- `ssleay32.dll` (ssl) + `ssleay32.pdb` for symbol names

Additionally, we need libc from the compiler install folder with the common functions (e.g. `strcpy`):
- `libcmt.lib` + `libcmt.pdb` for symbol names

## Detailed analysis (Ghidra)

We use the following convention while renaming unknown functions: `FUN_00540490` --> `FUN_00540490__strcpy`.

We start by sorting the functions by reference count and by renaming a couple of std lib functions that are used hundreds of times in the code.

Note: some functions are already renamed by Ghidra's FID (FunctionID) analyzer. The Ghidra developers maintain some FID databases with common signatures.

![Functions (ref count)]({{site.baseurl}}/assets/spambot/functions-ref-count.png)

Renamed functions:

- `FUN_00540490_strcpy`
- `FUN_005404a0_strcat`
- `FUN_00540c70_strchr`
- `FUN_00540da0_str_str`
- `FUN_005410ca_sprintf`
- `FUN_00541f40_memset`
- `FUN_0053fe40_memcpy`

### `entry`, `WinMain`, initialization

Go to entry and identify [WinMain](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-winmain) based on the signature

```c
int entry(void)

{
...
  pauVar3 = (undefined1 (*) [16])__wincmdln();
  iVar2 = FUN_0046b060_WinMain(0x400000,0,pauVar3);
                    /* WARNING: Subroutine does not return */
  _exit(iVar2);
}
```

In `WinMain`:
- COM initialization via [CoInitialize](https://learn.microsoft.com/en-us/windows/win32/api/objbase/nf-objbase-coinitialize)
- `FUN_0046dd00_app_ctx_init`: init for multithreading

### Thread 3: SMTP sending engine

#### STARTTLS stripping

The SMTP authentication method is selected by searching the EHLO response string for keywords in order: `STARTTLS` --> `LOGIN` --> `CRAM-MD5` --> `AUTH PLAIN` (fallback).
Since the EHLO exchange occurs before TLS negotiation (i.e. in plaintext), a MITM attacker can strip `"STARTTLS"` from the server response, forcing the bot to fall back to `AUTH PLAIN` over an unencrypted connection.

| State | Method | Trigger |
|---|---|---|
| `0x13B0` | `STARTTLS` | `strstr(response, "STARTTLS") != NULL` |
| `0x13C4` | `AUTH LOGIN` | `strstr(response, "LOGIN") != NULL` |
| `0x13CE` | `CRAM-MD5` | `strstr(response, "CRAM-MD5") != NULL` |
| `0x13BA` | `AUTH PLAIN` | fallback |

#### Traditional PKWARE Encryption (ZipCrypto)

Another high vulnerability is the use of the traditional PKWARE Encryption (ZipCrypto).

#### Predictable PRNG seed

Additionally, the PRNG used by ZipCrypto is predictable. This is a high vulnerability (though largely redundant since ZipCrypto is already broken independently).

`srand(time(NULL))` seeds once with a Unix timestamp. `rand()` is fully deterministic from the seed. A single 32-bit state updated via `_holdrand = _holdrand * 0x343FD + 0x269EC3` with no entropy mixed after seeding. The bot's `Date:` header leaks the approximate seed. ### Dead/unused crypto

The `capa` matches for `RC4` are false positives. The matched functions are zlib/deflate internals.

The config extractor uses byte-signature pattern matching to locate and extract all values directly from the binary. No addresses, keys or strings are hardcoded in the script. This makes it resilient to recompilation or minor patching across variants.

| Value | Signature | Extraction |
|---|---|---|
| Blowfish key | 16× `C6 45 xx yy` (consecutive `MOV byte [EBP+off], imm8`) validated by `6A 10` (`PUSH 16`) nearby | Read the immediate byte from each instruction. |
| Resource ID | `6A 0A 68 [ID] 6A 00 FF 15` (`PUSH RT_RCDATA; PUSH id; PUSH 0; CALL [FindResourceA]`) | Read 4-byte immediate after `0x68`. |
| XOR key | `6A xx 68 [VA] 8D 45 EC 50 E8` (`PUSH len; PUSH addr; LEA EAX,[EBP-0x14]; PUSH; CALL md5_hash`) | Resolve VA to string, compute `MD5(string)`. |
| Fake relay domains | `55 8B EC B8 D0 12 00 00 E8` (function prologue with unique 0x12D0 stack frame) | Scan function body for MOV instructions referencing `.rdata`, walk back to string start, filter by domain regex. |
